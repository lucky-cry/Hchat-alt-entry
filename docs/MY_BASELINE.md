# 我的维护基线（MY_BASELINE）

本文件记录「我这条线」的基线状态，改代码或升级微信后按这里回归。

## 1. 基线来源

| 项 | 值 |
|---|---|
| 起点 | 上游 `ljh520134/Hchat-alt-entry` 的 `alt-entry` 分支，提交 `7bbf5d9` |

| 与 6.4.1 的差异 | 只多 `link_parse`（链接解析）与 `restore_legacy_chat_input`（旧版聊天输入框），**两者默认关闭** |

## 2. 版本号与签名

```text
正式包：versionName 6.4.x（workflow 自动递增），versionCode = 600 + run_number
测试包：versionName test.N，versionCode = 600 + run_number（与正式包共用同一递增序列，
       按构建先后自然递增，互相覆盖都不会被判降级）
签名：自有 app/keystore/release.jks（不进仓库），密码走 GitHub Secrets
```

> 官方版是 591，从 600 段起步可以覆盖安装**自己**后续的包；但与官方签名不同，首次仍必须卸载官方版。


## 5. 每次改动的流程

1. 从 `my/stable` 拉 `fix/<问题短名>`。
2. 只改与问题相关的文件；公共层（`hooks/api`、`core`）改动单独提交并全量回归。
3. 无 R8 测试包验证 → 正式 R8 包再验证（keep 规则漏了只有正式包会崩）。
4. 提交信息写清：问题 / 修改 / 根因 / 逆向依据 / 测试 / 未验证。
5. 合回 `my/stable`，出包后打 tag `v6.4.x`，APK 存 GitHub Release 留作回滚。

## 6. 微信升级后的顺序

1. 先只跑第 4 节清单，记录哪些功能掉了。
2. 日志过滤 `[Hchat:` 与 `DexFinder为空` / `功能安装失败`，判断是「定位失败」还是「行为变化」。
3. 定位失败才改 `DexFinder` / 功能内定位条件；优先按参数个数和字符串锚点分支，不用 versionCode 硬判断。
4. 结论写进 `docs/`（可参考上游的 `*_EVIDENCE.md` 写法）。
