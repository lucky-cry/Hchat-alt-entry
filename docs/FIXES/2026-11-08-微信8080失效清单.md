## 2. 分层结论

```
共享层（修一次带一片）
├── A. 数据库包装层 wrapper 未挂上 → #1，连带 #7 #8，以及所有「消息入库/变更」类功能
└── B. 网络派发器未定位 → #2，牵连需要主动发请求的功能（红包/转账领取等）

功能层（各自独立定位）
├── 视频号详情（FinderFeedDetailResolver 候选 0）
├── 自动礼物（GiftMessageHook 找不到消息类）
├── 脚本发送按钮（ChatFooter 入口）
├── 聊天分组（会话父级读取）
└── 红包/礼物/屏蔽消息/骰子/已读/免打扰（DexInstall 重试耗尽）
```

## 3. 静态验证（用手机上的微信 8.0.80 APK 做的）

- 模块所有 22 个 DexKit 字符串锚点 **全部仍存在**（`scripts/check_wechat_anchors.py`）。
- 数据库包装类：两个锚点 `MicroMsg.SqliteDB` / `sql is null ` 仍在同一类 `ai5/d0`，且
  `l(String,String,ContentValues)->long`、`p(String,ContentValues,String,String[])->int`、
  `delete(String,String,String[])->int` 都符合模块的签名匹配条件。
  → **不是签名变了，也不是锚点丢了**，更可能是解析时机 / loadClass / 钩子安装环节。
- 因此 #1 需要一次带诊断日志的构建来定位（`wrapper=null` 还是「类找到了但钩子 0 个」）。

## 4. 修复计划

1. **第一轮（诊断 + 共享层）**
   - 在 `WeChatDatabaseListenerApi.install()` 入口补日志：`isAvailable` / `classLoader` / `wrapperClass` / 各计数。
   - 在 `DexFinder.resolveDatabaseApi()` 补日志：`sqlite=` 是否为 null、查询耗时。
   - 出无 R8 包 → 实机抓日志 → 定位 #1 真因。
2. **第二轮（共享层收尾）**
   - #2 网络派发器：检查 `sendNetworkRequest` 的 dispatcher 定位条件，按 8.0.80 的新结构放宽。
   - 修好 #1/#2 后回归 #7 #8，确认自动恢复。
3. **第三轮（功能层逐个）**
   - 视频号详情、自动礼物、脚本发送按钮、聊天分组、红包/骰子/已读/免打扰/屏蔽消息。
   - 每个都按 `docs/FIXES/BUG_LIST.md` 的字段记录，改完在本文追加结论。

## 5. 备注

- 模块自身没有硬编码微信版本分支，所以不存在「版本判断走错」。
- 本机已缓存 8.0.80 APK 的 dex 解析结果，后续可按需查任意类/方法签名：
  `python3 scripts/dex_string_refs.py <微信.apk> "<字符串>"`
